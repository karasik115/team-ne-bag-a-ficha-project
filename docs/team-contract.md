# Правила взаимодействия команды

**Команда:** «Не баг, а фича»  
**Бригада:** № 1  
**Дисциплина:** «Введение в профессиональную деятельность»

## Коммуникация

Для оперативного решения задач команда использует общий рабочий чат в Telegram. Сложные технические вопросы и плановые встречи обсуждаются в голосовом канале Discord.

## Ежедневное взаимодействие

1. Каждый день в удобное время каждый участник кратко сообщает в рабочем чате, что сделал вчера, что планирует сделать сегодня и какие возникли проблемы.
2. В рабочее время участники отвечают на сообщения в течение 2–3 часов.
3. При разногласиях лидер команды принимает решение после обсуждения с менеджером либо вопрос выносится на общее голосование.

## Обсуждение задач и соблюдение сроков

Менеджер координирует сроки сдачи и коммуникацию с преподавателем, лидер отвечает за конечный результат. Перед началом задачи участник уточняет ожидаемый результат и срок в рабочем чате. При возникновении трудностей он сообщает о них команде, чтобы согласовать дальнейшие действия. Конкретные сроки определяются по заданиям преподавателя и фиксируются командой.

## Работа с репозиторием

1. Все восемь практических работ хранятся в одном репозитории. Каждый участник поддерживает порядок в своих разделах.
2. Перед началом работы участник обновляет локальную копию основной ветки: `git switch main`, затем `git pull origin main`.
3. Изменения выполняются в собственной ветке `feature/<имя_участника>` или `role/<название_роли>`. Фактические названия приведены в [описании ролей](roles-and-responsibilities.md).
4. Коммит должен иметь осмысленное сообщение: например, `docs: уточнить обязанности менеджера` или `feat: добавить сценарий прототипа`.
5. После отправки ветки на GitHub участник открывает Pull Request в `main`, описывает изменения и получает ревью от другого участника.
6. Автор Pull Request не заменяет независимое ревью собственной проверкой. Если изменения внёс лидер, их сначала проверяет другой участник.
7. После проверки слияние выполняет лидер команды. Конфликты решаются с участием авторов соответствующих изменений.
8. Отчёты размещаются в `report.md`, иллюстрации и скриншоты в `assets/`, исходный код в `src/`. Служебные и временные файлы исключаются через `.gitignore`.
9. Участники своевременно отправляют свои коммиты на GitHub и сохраняют актуальные локальные копии. Для независимой резервной копии можно использовать архив репозитория или локальное зеркало; `push` сам по себе не заменяет отдельную резервную копию.

Распределение ответственности за эти действия приведено в [матрице RACI](raci-matrix.md).
